# Архитектура Guardian

Guardian - HTTP forward-прокси с поддержкой HTTPS через CONNECT-туннели без расшифровки TLS. C4-модель: [c4.md](./c4.md). Настройки, эндпоинты и ограничения: [instruction.md](./instruction.md).

## Потоки данных

1. Клиент -> необязательный балансировщик -> обработчик прокси (`:8080`).
2. Обработчик: определение IP -> лимит одновременных обработок по IP -> размер тела -> RPS по IP -> проверка токена -> пользовательская квота и RBAC -> Filter Engine.
3. Первое совпавшее правило по убыванию приоритета определяет действие. `block` завершает обработку; при отсутствии совпадения запрос разрешается.
4. Для HTTP действие `modify` меняет заголовки запроса. При включённом кэше возможен ответ из кэша; иначе выполняются SSRF-проверка и пересылка upstream. Подходящий ответ сохраняется до замены тела по `modify`.
5. Для CONNECT после фильтрации выполняются SSRF-проверка и открытие TCP-туннеля. `modify` не применяется. TLS не расшифровывается: запросы внутри туннеля не фильтруются и отдельно в RPS не учитываются.
6. Admin API (`:8081`): JWT либо внешний токен, RBAC, CRUD правил и пользователей, тест правила и статистика. `/health` и `/ready` доступны без токена.
7. Метрики (`:9090`): `/metrics` и `/health`, без аутентификации.

## Хранение и обновление состояния

- PostgreSQL хранит пользователей, правила, аудит и журналы запросов. При настроенной реплике чтения запросы правил и пользователей также направляются на неё. Задержка репликации влияет на время применения изменений.
- Рабочий набор правил находится в памяти Filter Engine. Он загружается из БД при запуске, после изменений на текущем экземпляре и периодически на каждом экземпляре (`cache.rules_ttl`). Снимок записывается также в кэш, но штатная перезагрузка читает БД.
- Кэш токенов и HTTP-ответов использует локальную память и, если доступен, Redis. `cache.enabled` управляет только включением кэша ответов совместно с `response_enabled`.
- Аудит асинхронно записывается в PostgreSQL. Журналы запросов записываются туда при `log.persist_requests: true`. Оба вида событий публикуются в Kafka при `queue.enabled: true` и `queue.backend: kafka`. Ответ клиенту не зависит от результата записи; часть событий может быть потеряна при ошибке хранилища или остановке процесса.
- Попадания в кэш ответов и отказы при аутентификации и проверке лимитов до фильтрации не попадают в `request_logs`. Статистика БД и метрики поэтому охватывают разные наборы событий.

## Безопасность и ограничения

- При HTTP forward удаляются hop-by-hop-заголовки, `Authorization` и `Proxy-Authorization`. Данные внутри CONNECT-туннеля не обрабатываются.
- При `proxy.allow_private_targets: false` блокируются частные и локальные адреса, CGNAT/ULA, имена localhost/`.local` и цели с ошибкой DNS. Проверка DNS отделена от подключения и не закрепляет проверенный IP за dialer; полной защиты от DNS rebinding нет.
- IP клиента берётся из XFF/X-Real-IP только при подключении через `server.trusted_proxies`.
- Изменение пользователя в PostgreSQL не обновляет поля ранее выданного JWT. Текущий `updateUser` сразу удаляет записанное переопределение активности из кэша; изменение `active` и удаление пользователя не обеспечивают отзыв токенов.
- Результат проверки токена хранится в течение `auth.token_cache_ttl`. В текущей реализации TTL кэша не ограничен полем `exp`: при попадании в кэш срок действия JWT повторно не проверяется. Поэтому истёкший JWT может приниматься до истечения TTL кэшированного результата проверки.
- `/ready` отражает внутренний флаг запуска/остановки, а не текущую доступность БД, Redis или IdP.

## Масштабирование и лимиты

Пользовательских сессий в процессе нет, но правила, кэш, локальные ограничители и соединения имеют локальное состояние. Открытые туннели между репликами не переносятся. Kubernetes-манифест задаёт HPA с целевой средней загрузкой CPU 70% от requests.

При доступном Redis RPS ограничивается общим счётчиком с секундным окном. При отключении Redis или ошибке счётчика используется локальный token bucket с `burst`; общий лимит кластера тогда не гарантируется. `rate_limit.enabled: false` отключает RPS, но не `max_conns_per_ip`.

`ConnTracker` ограничивает одновременные вызовы обработчика на одном экземпляре. После передачи соединения обработчику туннеля (hijack) открытый CONNECT-туннель в этом лимите не учитывается.

## Производительность

Используются `fasthttp`, DNS-кэш dialer, пулы соединений и буфер копирования туннеля (по умолчанию 32 KiB). `quota_rps` берётся из токена без чтения пользователя на каждый запрос. Кэш HTTP-ответов выключен по умолчанию. Доступные результаты измерений и условия их интерпретации приведены в [test-result.md](./test-result.md).
