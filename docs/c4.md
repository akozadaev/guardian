# C4-модель: Guardian Proxy

Диаграммы [C4](https://c4model.com/) показывают окружение Guardian, развёртываемые сервисы и компоненты процесса. Последовательность обработки запроса представлена отдельно в flowchart. Для просмотра нужен рендерер Mermaid с поддержкой C4 и flowchart.

Связанные материалы: [architecture.md](./architecture.md), [ТЗ](../doc/task.md).

---

## Уровень 1. Контекст системы

Клиенты обращаются к целевым серверам через Guardian. Администратор управляет правилами и пользователями через Admin API; служба эксплуатации получает метрики и проверяет состояние сервиса.

```mermaid
C4Context
title Guardian - System Context

Person(client, "HTTP Client", "Браузер, SDK, curl - трафик через прокси")
Person(admin, "Administrator", "Управляет правилами, пользователями, смотрит stats")
Person(ops, "SRE / Ops", "Мониторинг, алерты, масштабирование")

System(guardian, "Guardian Proxy", "HTTP forward-прокси и CONNECT без расшифровки TLS, RBAC, аудит")

System_Ext(upstream, "Upstream Origin", "Целевые HTTP/HTTPS сервисы в интернете")
System_Ext(oauth, "OAuth2 / IdP", "Выдача токенов; JWKS или introspection для Guardian")
System_Ext(lb, "Load Balancer", "HAProxy / Nginx / cloud LB перед экземплярами")

Rel(client, lb, "HTTP proxy requests / CONNECT для HTTPS", "HTTP поверх TCP")
Rel(lb, guardian, "Round-robin / leastconn", "HTTP")
Rel(admin, guardian, "Admin REST API + Bearer", "HTTP :8081, TLS через внешний LB")
Rel(guardian, upstream, "Forward / tunnel", "HTTP/TLS")
Rel(guardian, oauth, "Загрузка JWKS / introspection (опц.)", "HTTPS")
Rel(ops, guardian, "Метрики и проверки состояния", "HTTP :9090 metrics/health, :8081 health/ready")

UpdateRelStyle(client, lb, $offsetY="-20")
```

### Участники и внешние системы

| Актор / система | Роль относительно Guardian |
|-----------------|----------------------------|
| HTTP Client | Источник проксируемого трафика |
| Administrator | CRUD правил и пользователей |
| Upstream | Назначение после allow/modify |
| OAuth2 / IdP | Внешний источник токенов; альтернативный локальный режим HS256 реализован в Guardian |
| Load Balancer | Горизонтальное масштабирование нескольких экземпляров |
| SRE | Наблюдаемость и HPA |

## Уровень 2. Контейнеры

Прокси, хранилища и сервисы мониторинга развёртываются отдельно. Балансировщик направляет запросы на экземпляры Guardian.

```mermaid
C4Container
title Guardian - Containers

Person(client, "HTTP Client")
Person(admin, "Administrator")
Person(ops, "SRE")

System_Boundary(g, "Guardian Platform") {
    Container(lb, "Load Balancer", "HAProxy / Nginx", "Балансировка, health checks")
    Container(proxy, "Proxy Instance", "Go, fasthttp", "Фильтрация, проксирование, Admin API, метрики")
    ContainerDb(pg, "PostgreSQL 16", "RDBMS", "users, rules, audit_logs, request_logs")
    ContainerDb(redis, "Redis", "Cache", "auth tokens, rules snapshot, rate keys, response cache")
    Container(kafka, "Kafka (optional)", "Kafka", "async request/audit events")
    Container(prom, "Prometheus", "Metrics TSDB", "Сбор guardian_* метрик")
    Container(grafana, "Grafana", "Dashboards", "Визуализация (опц.)")
}

System_Ext(upstream, "Upstream Origin")
System_Ext(oauth, "OAuth2 / IdP")

Rel(client, lb, "HTTP proxy traffic")
Rel(lb, proxy, ":8080 proxy, :8081 ready")
Rel(admin, proxy, "REST /api/v1", ":8081")
Rel(ops, prom, "Query metrics")
Rel(prom, proxy, "scrape /metrics", ":9090")
Rel(grafana, prom, "Запросы к источнику метрик")
Rel(proxy, pg, "SQL via pgxpool")
Rel(proxy, redis, "Кэш GET/SET TTL и RPS-счётчики")
Rel(proxy, kafka, "Publish events")
Rel(proxy, upstream, "Forward / CONNECT")
Rel(proxy, oauth, "JWKS / introspection (опц.)")
```

### Порты экземпляра Guardian

| Порт | Контейнерная ответственность |
|------|------------------------------|
| `:8080` | Публичный прокси (HTTP + CONNECT) |
| `:8081` | Admin API, `/health`, `/ready` |
| `:9090` | Prometheus `/metrics`, `/health` |

### Масштабирование

- **Proxy Instance** - горизонтально: пример HPA задаёт целевую среднюю загрузку CPU 70% от requests.
- **PostgreSQL** - primary и опциональная read replica для всех операций чтения, включая правила и пользователей.
- **Redis** - общий кэш для экземпляров.
- **Kafka** - опционально; публикация при `queue.enabled=true` и `queue.backend=kafka`; иначе используется NopPublisher.

## Обработка запроса на уровне кода

Уровень кода для одного входящего запроса на `:8080` (упрощённо).

```mermaid
flowchart TD
    A[RequestCtx: IP клиента] --> B{ConnTracker допускает?}
    B -->|нет| R429[429]
    B -->|да| C{Размер тела допустим?}
    C -->|нет| R413[413]
    C -->|да| D{RPS по IP допускает?}
    D -->|нет| R429
    D -->|да| E{Authorization передан?}
    E -->|нет| F{Auth обязателен?}
    F -->|да| R401[401]
    F -->|нет| G[Filter Engine]
    E -->|да| V{Токен валиден?}
    V -->|нет| F
    V -->|да| Q{Квота пользователя допускает?}
    Q -->|нет| R429
    Q -->|да| P{Есть право proxy:access?}
    P -->|нет| R403[403]
    P -->|да| G
    G --> H{Первое совпадение: block?}
    H -->|да| BL[Ответ правила: по умолчанию 403]
    H -->|нет| J{CONNECT?}
    J -->|да| K[SSRF-проверка и открытие туннеля]
    K -->|ошибка| R502[502]
    K -->|успех| T[200, hijack, TCP-туннель без анализа TLS]
    J -->|нет| M[modify заголовков, если задан]
    M --> CC{Есть подходящий ответ в кэше?}
    CC -->|да| CR[Ответ из кэша и метрики, без request_log]
    CC -->|нет| S{SSRF-проверка пройдена?}
    S -->|нет| R403
    S -->|да| U[Удаление служебных заголовков и ForwardHTTP]
    U -->|ошибка| R502
    U -->|успех| W[Кэширование до modify тела]
    W --> X[modify тела, если задан]
    X --> O[Метрики и асинхронный request_log]
    T --> O
```

Диаграмма показывает логические этапы обработчика; ограничения RPS выполняются только при `rate_limit.enabled: true`. Лимит размера тела также применяется сервером до вызова обработчика. `ConnTracker.Release` выполняется при выходе из обработчика, поэтому не учитывает время жизни туннеля после hijack. Для CONNECT метрики длительности и журнал отражают открытие туннеля.

Ключевые типы и функции:

| Шаг | Символ |
|-----|--------|
| IP | `netutil.ClientIP`, `ratelimit.ConnTracker` |
| Auth | `auth.Service.ValidateToken`, `TokenClaims.QuotaRPS` |
| Filter | `filter.Engine.Evaluate`, `models.ConditionNode` |
| Forward | `proxy.Core.ForwardHTTP`, `ErrPrivateTarget` |
| Tunnel | `proxy.Core.HandleCONNECT` |

## Развёртывание

Пример с тремя репликами Guardian за балансировщиком. PostgreSQL, Redis и Kafka общие для реплик. Grafana запрашивает метрики у Prometheus.

```mermaid
flowchart LR
    subgraph Internet
        CL[Clients]
    end
    subgraph Edge
        LB[HAProxy / Cloud LB]
    end
    subgraph K8s["Kubernetes namespace"]
        P1[Proxy pod]
        P2[Proxy pod]
        P3[Proxy pod]
        HPA[HPA CPU 70%]
    end
    subgraph Data
        PG[(PostgreSQL)]
        RD[(Redis)]
        KF{{Kafka optional}}
    end
    subgraph Observability
        PR[Prometheus]
        GR[Grafana]
    end

    CL --> LB --> P1 & P2 & P3
    HPA -.-> P1 & P2 & P3
    P1 & P2 & P3 --> PG & RD & KF
    PR --> P1 & P2 & P3
    GR --> PR
```

## Связь диаграмм с реализацией

Рабочий набор правил находится в памяти процесса и обновляется из PostgreSQL. Redis используется для кэширования и общих RPS-счётчиков; открытые соединения и резервные ограничители остаются локальными. Направление связей на диаграммах показывает, какой компонент обращается к другому.

CONNECT передаёт TCP-трафик без расшифровки TLS. Диаграмма обработки описывает открытие туннеля; запросы внутри него не проходят через Filter Engine повторно.

Ограничения реализации проверки и отзыва токенов, SSRF-проверок, аудита и readiness приведены в [architecture.md](./architecture.md). Настройки и примеры запуска - в [instruction.md](./instruction.md).
