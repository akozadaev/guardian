# Руководство администратора

Подробные настройки и эндпоинты: [instruction.md](./instruction.md). Схемы Admin API: [openapi.yaml](./openapi.yaml).

## Роли

| Роль | Права |
|------|-------|
| `admin` | rules read/write, users read/write, stats, proxy |
| `moderator` | rules read/write, stats, proxy |
| `user` | rules read, stats, proxy |
| `guest` | только proxy |

## Получение и передача токена

При `auth.oauth2_enabled: false` используется локальный JWT HS256. При включённом внешнем валидаторе используются JWT через JWKS либо токены через introspection; автоматического перехода к локальному HS256 нет. Получение токена у IdP выполняет клиент: Guardian не реализует форму входа или Authorization Code Flow.

Внешний токен должен содержать `user_id` либо `sub` в формате UUID и распознаваемую `role` или массив `roles`. Из массива выбирается наиболее привилегированная известная роль. Поддерживаемые имена и псевдонимы определены в `internal/auth/oauth2.go`. Introspection требует `active: true`; в JWKS-режиме отсутствие `active` означает `true`. Значение `auth.jwt_issuer` используется для проверки `iss` в JWKS-режиме.

Для локального bootstrap задайте сильный `GUARDIAN_AUTH_JWT_SECRET` и `GUARDIAN_AUTH_BOOTSTRAP_TOKEN`, затем запросите токен существующего активного пользователя:

```bash
curl -X POST http://127.0.0.1:8081/api/v1/auth/token \
  -H "X-Bootstrap-Token: $GUARDIAN_AUTH_BOOTSTRAP_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@guardian.local"}'
```

Без `auth.bootstrap_token` API возвращает `404`. Механизм предназначен для разработки и начальной настройки; автоматического отключения в рабочем окружении нет. При внешнем валидаторе выданный локальный bootstrap-JWT не проходит штатную проверку HS256.

Admin API принимает `Authorization: Bearer <token>`. На прокси аутентификация обязательна при `auth.require_auth_for_proxy: true`. Для HTTP передайте `curl -H "Authorization: Bearer $TOKEN"`; для HTTPS через CONNECT - `curl --proxy-header "Authorization: Bearer $TOKEN"`. В обоих случаях задайте `-x http://127.0.0.1:8080` и целевой URL.

## Правила фильтрации

- Первое совпавшее включённое правило по убыванию `priority` определяет действие; без совпадений запрос разрешается. Не полагайтесь на порядок правил с одинаковым приоритетом.
- `AND`/`OR` требуют хотя бы одного дочернего условия, `NOT` - ровно одного. Максимальная глубина дерева ограничена валидатором.
- Поля: `method`, `url`, `path`, `query`, `host`, `ip`, `content_type`, `body_size`, `body`, `header.*`, `user_id`, `role`. `ip` означает IP клиента, а не upstream.
- Операторы: `eq`, `neq`, `in`, `not_in`, `contains`, `prefix`, `regex`, `gt`, `lt`, `exists`.
- `allow` разрешает запрос, `block` возвращает ответ правила (`403` по умолчанию), `modify` меняет заголовки HTTP-запроса и/или тело HTTP-ответа.
- HTTPS не расшифровывается: правила проверяют запрос CONNECT, а не содержимое туннеля. `modify` для CONNECT не применяется.

[examples/rules.json](./examples/rules.json) содержит массив примеров. `POST /api/v1/rules` принимает **одно правило**, а не массив. Второе правило относится к роли `guest` из проверенного токена; анонимный запрос имеет пустую роль и не совпадает с ним. Проверка `/admin/` относится к целевому HTTP-сервису и не защищает Admin API Guardian.

Для `POST /api/v1/rules/{id}/test` поле `body` контекста передаётся как Base64-строка (Go `[]byte`), например `"body":"aGVsbG8="`. `body_size` задаётся отдельно; контекст теста не строится автоматически из URL/тела. Ответ: `{"matched":true,"action":"block"}`.

Изменения правил применяются сразу на обработавшем запрос экземпляре после успешной перезагрузки из БД; остальные экземпляры обновляются по `cache.rules_ttl`. При read replica учитывайте задержку репликации.

## Квоты и лимиты

`quota_rps` берётся из проверенного токена при включённом `rate_limit.enabled`. Значение ≤ 0 означает `rate_limit.default_rps`. При создании пользователя API заменяет нулевую квоту на 1000 и принудительно задаёт `active: true`. Для CONNECT учитывается только создание туннеля.

При доступном Redis RPS-счётчики общие; при ошибках Redis или его отключении ограничители локальные. `burst` действует только в локальном режиме. `max_conns_per_ip` ограничивает параллельные вызовы обработчика на экземпляре, но не время жизни открытого туннеля; отключение RPS не отключает этот лимит.

## Trusted proxies

Укажите конкретные IP/CIDR доверенных балансировщиков в `server.trusted_proxies`. При подключении с недоверенного IP XFF/X-Real-IP игнорируются при определении IP клиента. Не включайте в список сети, из которых клиенты могут подключаться напрямую.

## Изменение пользователя и отзыв токена

`PUT /api/v1/users/{id}` заменяет поля пользователя: пропущенные поля получают нулевые значения. Передавайте полный набор редактируемых полей (`email`, `role`, `active`, `quota_rps`). Изменение роли или квоты в PostgreSQL не обновляет поля ранее выданного JWT. Для применения новых значений требуется выдать новый токен.

`updateUser` записывает переопределение активности в кэш и сразу удаляет его вызовом `InvalidateUserCache`. Поэтому `active: false` и удаление пользователя не обеспечивают отзыв уже выданных токенов. Bootstrap при этом не выдаёт новый токен неактивному пользователю.

`POST /api/v1/auth/logout` помечает конкретный предъявленный токен как отозванный на 24 часа. Это локальный отзыв Guardian, а не отзыв у IdP. При отсутствии общего Redis отметка действует только на данном экземпляре. TTL кэшированного результата проверки не ограничен полем `exp` JWT. При попадании в кэш срок действия повторно не проверяется, поэтому истёкший JWT может приниматься до истечения `auth.token_cache_ttl`. Это ограничение реализации проверки токенов в Guardian.

## Мониторинг и аудит

`/health` и `/ready` находятся на admin-порту `:8081`; `/metrics` и дополнительный `/health` - на `:9090`. Readiness не проверяет текущую доступность зависимостей.

Метрики и `/api/v1/stats` относятся к одному экземпляру. `guardian_rule_hits_total` учитывает только `block`; статистика правил из PostgreSQL считает все записанные совпадения по `rule_id`. Для статистики БД нужны `request_logs` (`log.persist_requests: true`); попадания в кэш ответов и отказы при аутентификации и проверке лимитов до фильтрации в них не записываются. Аудит действий записывается асинхронно независимо от `persist_requests`; при ошибке записи или остановке процесса часть событий может быть потеряна.
